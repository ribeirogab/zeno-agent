# Linear Connector — Plan

**For this spec:** `[[spec]]`

## Approach

A catalog-only addition. No new code paths in worker, API, or dashboard. The remote-transport infrastructure from spec 0033 + the `authCheckTool` plumbing from spec 0038 already do everything Linear needs. The "implementation" is:

1. Add a JSON entry to `agent/connectors-catalog.json`.
2. Run the regenerator script to populate `tools[]` and the test snapshot from the live MCP.
3. Drop the brand icon SVG.
4. Verify quality gate + smoke.

If anything new surfaces during smoke (e.g., the dashboard install modal can't render a multi-line `Bearer ...` value cleanly), it gets handled as a follow-up — not in this spec.

## Phase ordering

### Phase 0 — Spec finalization (3-review loop)

Same protocol as 0037/0038. Faster cycles expected because the spec is small.

### Phase 1 — Catalog entry

- Append the `linear` connector to `agent/connectors-catalog.json`. Initial `tools: []` (regenerator fills it).
- `authCheckTool: 'list_teams'`.
- `secrets: [__MCP_AUTHORIZATION__]` with help text instructing the user to include `Bearer ` prefix.
- `transport: 'remote'`, `transportConfig: { url: 'https://mcp.linear.app/mcp' }`.
- `tags: ['issues', 'project-management']`.

### Phase 2 — Tool list regeneration

- **Pre-step (script patch)**: edit `apps/worker/scripts/regenerate-catalog-tool-snapshots.mjs`. Change:
  ```js
  if (!value) {
    throw new Error(
      `--fetch-from-mcp: missing env var ${envName} for catalog entry "${entry.id}"`,
    );
  }
  ```
  …to:
  ```js
  if (!value) {
    console.warn(
      `skip ${entry.id}: missing env var ${envName} (set it to fetch tools for this entry)`,
    );
    continue;
  }
  ```
  Skipping leaves the entry's existing `tools[]` untouched in the catalog (writeCatalog rewrites the whole file but only this loop reassigns `entry.tools`); writeSnapshot then mirrors what's in the catalog, which for skipped entries is the prior tools list.
- Run: `__MCP_AUTHORIZATION__="Bearer lin_api_xxx" node apps/worker/scripts/regenerate-catalog-tool-snapshots.mjs --fetch-from-mcp`.
- Sentry is skipped (warning log line); Linear is fetched. Diff to inspect: only Linear's `tools[]` and the Linear key in the snapshot.
- **Note about credential validation during regen**: the regenerator calls `discoverTools(transient, secrets)` WITHOUT the `authCheckTool` option (line 118 of the script). That means it only does `initialize` + `tools/list`, not the auth-check tool probe. A token that's syntactically valid but not authorized may pass regen silently with a partial/empty tool list. **Real credential validation lives in Task 5.2's API smoke** (`POST /catalog/:id/test`), which DOES pass `authCheckTool` per spec 0038 F#2. The implementer should treat regen as "populate tool list assuming a known-good key" and rely on the API test endpoint as the deterministic auth check.
- **Note about env var naming**: the regenerator's convention (per spec 0038) is "env var name = first required secret key". For Linear, that key is `__MCP_AUTHORIZATION__`, which is not a normal env var name (it has underscores wrapping). The cleanest path is to set it as `__MCP_AUTHORIZATION__=Bearer\ lin_api_xxx` in the env where the script runs. Since `__MCP_AUTHORIZATION__` is a string with `__` prefix, shells handle it fine.
- **Note about how the value flows (remote vs stdio)**: For `transport: 'remote'` entries like Linear, the regenerator passes the secret to `discoverTools`, which calls `toRemoteConfig`. That function intercepts the reserved key `__MCP_AUTHORIZATION__` (see `packages/mcp-discover/src/build-config.ts`) and places its value in `headers.Authorization`. The reserved key is **not** forwarded as an env var to any subprocess — there is no subprocess for remote transport. For stdio entries (Sentry, future Klaviyo/Swarmia/GitHub), the secret key IS the env var passed to the spawned MCP subprocess (e.g., Sentry's `SENTRY_ACCESS_TOKEN`). This distinction is internal to each transport's `build-config` path and doesn't affect how the regenerator sets up its env — but it matters when debugging.

### Phase 3 — Brand icon

- `curl -L -o agent/assets/connectors/linear.svg https://static.linear.app/integrations/mcp/icon.svg` (URL from the MCP's `serverInfo.icons` metadata).
- Verify the SVG renders in the browser at `/api/connectors/catalog/icons/linear.svg` — the existing icon-serving endpoint at `connectors.ts:204` already handles new files (it accepts any filename in the catalog's `icon` field).

### Phase 4 — Quality gate

- `pnpm -w run quality-gate` green. New tools[] in the catalog → P1.5 self-consistency test in spec 0037 Phase A still passes (the snapshot was regenerated in lockstep).

### Phase 5 — Manual smoke (live profile)

After redeploying the running container (so it picks up the catalog change):

1. **API smoke** (curl):
   - `POST /api/connectors/catalog/linear/test` with `Bearer lin_api_INVALID` → expect `{ok: false, errorKind: 'auth'}`.
   - Same with the real key → expect `{ok: true, tools: [<30+>], durationMs}`.
2. **UI smoke** (browser at `localhost:3001/connectors`):
   - Catalog card visible with Linear icon.
   - Click → modal opens with one secret field.
   - Paste `Bearer <real key>`, click Test → green strip with tool count.
   - Click Add → connector lands enabled.
3. **Runtime smoke** (Slack DM in `D0EXAMPLE000`):
   - Send "[smoke linear] me lista 3 issues do meu time".
   - Agent should call `mcp__linear__list_issues` (or similar), return real issue data.
   - Confirm `connector_invocations` row with `tool_name='list_issues' result='ok'`.

### Phase 6 — Close

- Spec status `shipped`.
- If any smoke step failed and got fixed: short learning note under `context/learnings/`.

## Risks / Open Decisions

- **Decision: brand icon source**. Using Linear's official MCP icon CDN (`static.linear.app/integrations/mcp/icon.svg`). Stable per their MCP, and the `serverInfo.icons` metadata blesses it as the canonical asset.
- **Decision: tool subset**. Accept all 30+ — no filtering. Concerned operators can change permissions per-tool in the detail page.
- **Risk: Bearer prefix UX**. Documented in spec; if smoke shows the user really fumbles this, follow up with an install-modal hint that auto-prepends.
- **Open: do we register a Slack-DM smoke as a recurring regression**? No — Slack-DM smoke against a live third-party service is the 0036 manual-runbook territory, not the per-PR CI.
