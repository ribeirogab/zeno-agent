# Skill-scoped credentials: self-contained auth inside the skill folder

A skill can carry its own credentials (AWS keys, API tokens, private keys) as files inside its directory. The skill's SKILL.md documents how to use them. No global env pollution, no cross-skill leakage.

## Context

Implemented for the `acme` skill: AWS read-only credentials, GitHub App private key, and Terraform IaC all live inside `profiles/fn/skills/acme/`. The skill is entirely self-contained — clone the profile dir to a new machine and everything works.

## How It Works

Example layout:
```
profiles/<name>/skills/acme/
├── SKILL.md                  # entrypoint — tells the agent how to auth
├── aws.md / github.md        # reference docs (progressive disclosure)
├── .aws/
│   ├── credentials           # generated by Terraform, gitignored
│   └── config                # generated by Terraform, gitignored
├── github-app.pem            # GitHub App private key, gitignored
└── terraform/                # IaC to provision the credentials
    ├── main.tf
    ├── modules/readonly-user/
    └── README.md
```

The skill tells the agent to set env vars per-command:
```bash
export AWS_CONFIG_FILE=/app/profile/skills/acme/.aws/config
export AWS_SHARED_CREDENTIALS_FILE=/app/profile/skills/acme/.aws/credentials
aws --profile fn sts get-caller-identity
```

This avoids relying on the container's default `~/.aws/` (which other skills might own).

## How to Apply

When a skill needs credentials:
1. Store them inside the skill's folder (never in `.env` or `~/.aws/` — those are global).
2. Document in SKILL.md exactly how the agent should export/reference them.
3. If credentials need provisioning (IAM users, API keys), put the IaC (Terraform, scripts) inside the skill too.
4. The entire skill folder is gitignored via `profiles/*/` — credentials never touch git.
5. For AWS: use `AWS_CONFIG_FILE` / `AWS_SHARED_CREDENTIALS_FILE` env vars pointed at the skill's files. For GitHub: use `GH_TOKEN=$SKILL_TOKEN` prefix. For other services: similar env-var scoping.
