# Dashboard Cleanup — Spec

**Status:** Draft
**Scope:** Three surgical fixes against the profile dashboard surface that landed alongside the multi-profile CLI: drop the now-unused auth layer (Q7 brainstorm decision the multi-profile-cli spec did not deliver), reorder the first-run setup checklist so Claude is configured before Slack, and stop hardcoding the sidebar version string so it reflects the running CalVer tag.

## Context

Three findings surfaced during the v2026.5.7-3 → v2026.5.7-5 E2E test on the operator's machine:

1. The multi-profile CLI spec ([[../2026-05-07-multi-profile-cli/spec]]) brainstorm Q7 locked on **option (b): no auth on profile dashboards** (bind 127.0.0.1, CSRF + `SameSite=Strict`). The spec then explicitly scoped out `apps/api` / `apps/dashboard` refactors — leaving the password login screen and `DASHBOARD_PASSWORD` env vars in place. Operators see "Identify yourself" with `changeme-please`, contradicting the brainstorm intent. This spec finishes the job.
2. The first-run setup checklist (`apps/dashboard/src/routes/_authed/index.tsx`) currently lists Slack as step 1 and "schedule your first cron" as step 2. The agent cannot reply at all without a configured backend (Claude OAuth), so Slack-before-backend is wrong-ordered. Reorder so step 1 routes to `/settings?tab=backend` (Connect Claude) and step 2 routes to Slack.
3. The sidebar logo strip displays `zeno · v0.3.1` from a hardcoded constant. The CLI is at `v2026.5.7-5`. Sidebar must read the running version from runtime, not a stale literal.

## Problem Statement

- The dashboard's password gate adds friction with zero security value when the runtime is bound to `127.0.0.1` on a single-user laptop. The Q7 decision is documented; the implementation is not.
- The setup checklist as shipped misroutes the operator: pasting a Slack token before configuring the backend produces a worker that boots but cannot reply.
- The sidebar version string lies. Operators cannot tell which release is actually running. Lying version strings break the upgrade-then-verify loop and erode trust in `zeno upgrade`.

## Non-Goals

- **Production-grade auth** for remote/tunneled deploys — backlog'd as `production-grade-auth-layer`. This spec only removes the cosmetic password gate, not the future signed-token mechanism.
- **Onboarding wizard** beyond the checklist reorder — the broader visual onboarding is its own future spec.
- **Refactor of unrelated dashboard routes** — only the routes touched by auth removal and the first-run home are in scope.
- **Versioning the api separately from the CLI** — the runtime container's `package.json` is already in lockstep with the CLI; sidebar reads a single source.
- **Changes to the runtime worker / backend code** beyond what is required to drop auth (notably: do not touch the Slack `NoopChannel` fallback shipped in `v2026.5.7-3`).

## Constraints

- TypeScript strict, biome, vitest. No new runtime deps.
- Repo is public; no real identifiers in committed examples (`vault/rules/sanitization.md`).
- Profile dashboards bind `127.0.0.1` only. Hardening MUST stay in place after auth removal: CSRF token on mutating routes, `SameSite=Strict` on session cookies (now used only for CSRF nonce), CSP without `unsafe-inline` scripts.
- Forward-only: this spec is a breaking change for any profile that already filled in `DASHBOARD_PASSWORD`. Pre-release notes will flag.
- Sidebar version must come from a **single canonical source** at runtime. The api already serves `/api/health`; either extend it with `version` or expose `/api/info`.
- Dashboard route tree (`apps/dashboard/src/route-tree.gen.ts`) is generated by TanStack Router — must be regenerated, not hand-edited.

## User Stories / Scenarios

1. **Fresh install reaches the dashboard without a password.** Operator runs `zeno start personal`, opens `http://localhost:6101`. The app loads directly into the home view (or onboarding redirect) — no "Identify yourself" screen, no password field.

2. **First-run checklist routes to Claude before Slack.** With no backend and no Slack installed, the operator lands on the home empty state. Step 1 reads "configure Claude backend" and CTA links to `/settings?tab=backend`. Step 2 reads "connect a Slack workspace". Step 3 reads "schedule your first cron". Counter at the right reads `0 of 3 complete · ~7 min`.

3. **Sidebar version reflects the installed release.** Running `v2026.5.7-5`, the sidebar logo strip reads `zeno · v2026.5.7-5` (gold dot before the version). After `zeno upgrade --to v2026.5.X`, the sidebar updates on next page load.

4. **Existing operator on a profile that already has `DASHBOARD_PASSWORD` set.** After the upgrade, that env var is ignored — no error, no warning, just dropped from runtime config. Operator's `.env` may still contain the line; the CLI's next `zeno start` will rewrite the file from `templates/profile/env.template` (which no longer includes the line) but operator-added keys survive verbatim per the multi-profile-cli `.env` rewrite rule.

## Acceptance Criteria

### Auth removal — apps/api

- [ ] `apps/api/src/routes/auth.ts` is deleted.
- [ ] `apps/api/src/auth/middleware.ts` is deleted.
- [ ] `apps/api/tests/auth/middleware.test.ts` is deleted.
- [ ] `apps/api/src/auth/hmac.ts` and `apps/api/tests/auth/hmac.test.ts` remain only if some non-auth feature still consumes the HMAC helper; otherwise delete. Repo-wide grep `from.*auth/hmac` confirms zero non-auth callers before deleting.
- [ ] `apps/api/src/config.ts` no longer references `DASHBOARD_PASSWORD` or `DASHBOARD_SESSION_SECRET` in the zod schema or anywhere else. The runtime boots without those env vars.
- [ ] `apps/api/src/server.ts` no longer mounts the auth middleware. The login route is not registered. Mutating routes still get a CSRF check via a CSRF middleware that validates a token cookie + `X-CSRF-Token` header.
- [ ] All `/api/*` routes that previously sat behind `requireAuth` are reachable without a session cookie when called from `127.0.0.1`.
- [ ] Repo-wide grep `DASHBOARD_PASSWORD\|DASHBOARD_SESSION_SECRET` returns matches only in historical specs under `vault/specs/`.

### Auth removal — apps/dashboard

- [ ] `apps/dashboard/src/routes/login.tsx` is deleted.
- [ ] `apps/dashboard/src/routes/_authed.tsx` is deleted.
- [ ] The three route files previously under `_authed/` (`index.tsx`, `settings.tsx`, `connectors.$id.tsx`) are moved to the route root (or kept under a non-authed prefix that imposes no guard). Their imports are updated; their behavior — including the `beforeLoad` redirect to `/onboarding/connect-claude` when no backend is configured — is preserved verbatim.
- [ ] `apps/dashboard/src/route-tree.gen.ts` is regenerated by TanStack Router (not hand-edited) and committed.
- [ ] `apps/dashboard/src/lib/use-channels.ts`, `use-backends.ts`, and any other client that posted to `/api/auth/login` no longer references that endpoint or any session-cookie handling.
- [ ] Loading the dashboard at `http://localhost:6101` directly renders the home view (or the `/onboarding/connect-claude` redirect when no backend is configured). No login screen.

### Templates + env contract

- [ ] `templates/profile/env.template` no longer contains `DASHBOARD_PASSWORD` or `DASHBOARD_SESSION_SECRET` lines.
- [ ] On a profile created with the new `templates/profile/env.template`, the rendered `~/.zeno/profiles/<profile>/.env` contains `ZENO_MASTER_KEY=<64-hex>`, the managed-by header, and the runtime keys (`LOG_LEVEL`, `WORKSPACE_DIR`, `LOGS_RETENTION_DAYS`) — and no DASHBOARD_* keys.

### CSRF + cookie hardening

- [ ] All mutating `/api/*` routes (anything not `GET` / `HEAD`) require an `X-CSRF-Token` header that matches a `csrf` cookie. Missing or mismatched token returns 403.
- [ ] The `csrf` cookie is `HttpOnly: false` (the dashboard JS reads it), `SameSite=Strict`, `Secure: false` (localhost), `Path=/`.
- [ ] The dashboard's `apiFetch` client automatically attaches the `X-CSRF-Token` header from the cookie on every mutating request.
- [ ] CSRF is skipped for `GET` / `HEAD`. Read endpoints remain unauthenticated.
- [ ] `apps/api` listens on `127.0.0.1:3000` only (already enforced by Docker port binding `127.0.0.1:6101->3000/tcp` from the multi-profile-cli spec — confirm and document in `SECURITY.md`).

### Setup checklist reorder

- [ ] In `apps/dashboard/src/routes/_authed/index.tsx` (or its post-move location), `FirstRunChecklist` renders three steps in this order:
  1. **configure Claude backend** — helper: "Zeno needs a Claude OAuth token to talk. Click below to authorize." CTA: "configure Claude →" linking to `/settings?tab=backend`.
  2. **connect a Slack workspace** — same helper as today; CTA "paste token →" still hits the existing Slack install path.
  3. **schedule your first cron** — same helper as today; CTA "+ new cron".
- [ ] The header counter reads `N of 3 complete · ~7 min` where N is computed from per-step completion (Claude configured / Slack installed / at least one active cron).
- [ ] Steps 2 and 3 are visually `disabled` / non-active until step 1 completes (`active={claudeConfigured}`, `active={claudeConfigured && slackInstalled}`).
- [ ] "Two steps below..." copy in `FirstRunHero` is updated to "Three steps below...".

### Sidebar version

- [ ] `apps/api` exposes the running version on `GET /api/health` (extend the existing route — no new endpoint) as `{ version: string }` where `version` is the literal value of `zeno-agent/package.json:version` prefixed with `v` (matches the format used in CLI `zeno --version`).
- [ ] `apps/dashboard/src/components/layout/dashboard-sidebar.tsx` reads the version from the existing `useHealth` hook, not a hardcoded constant. Until the first health call resolves, the sidebar shows `zeno · v…` (ellipsis), not a placeholder string with a number.
- [ ] Repo-wide grep `v0\.3\.1` returns matches only inside historical specs in `vault/specs/`.

### Quality gate

- [ ] `pnpm run quality-gate` (lint + typecheck + tests across all workspaces) exits 0.
- [ ] `pnpm --filter @zeno/dashboard build` produces `dist/` with no runtime errors.
- [ ] CI smoke (gated on Docker availability): build + boot a profile container, curl `http://localhost:6101/api/health` → 200 with a `version` field that matches the running tag.

### Migration / breaking change

- [ ] Pre-release notes for the spec's release flag the breaking change: profiles created against an older release with `DASHBOARD_PASSWORD` in their `.env` are unaffected at runtime (env var is ignored), but operators should remove the line manually if they want a clean `.env`.

## Risks and Mitigations

| Risk | Mitigation |
|---|---|
| TanStack Router route-tree regeneration drifts from manual route file moves, causing 404s on existing pages. | Delete `route-tree.gen.ts` entirely and re-run the generator; commit the regenerated file. Verify by spawning the dashboard locally and visiting every previously-`_authed` route. |
| Dropping the auth middleware exposes mutating routes to CSRF from any browser tab the operator has open. | CSRF token cookie + header check on all mutating endpoints. Documented in `SECURITY.md`. |
| Removing `DASHBOARD_PASSWORD` from `templates/profile/env.template` breaks any operator who upgrades a running container without restarting (the old worker still expects the env var). | The runtime config schema is updated in lockstep — `apps/api/src/config.ts` no longer requires the env var. Old containers running the old image keep working until the operator runs `zeno restart <profile> --build`. |
| Sidebar version pulled from `/api/health` could lag the actual binary version (cache, stale request). | `useHealth` is already the source of truth for the runner heartbeat — same staleness window applies. Acceptable; a stale-by-30s version display is far better than a hardcoded literal. |
| Hardcoded `v0.3.1` is referenced in tests or screenshots. | Repo-wide grep before merging; update or delete any references. |

## Open Questions

None. The three changes are independent, the brainstorm decision (Q7) is already locked, and the runtime version source (`/api/health` extended with `version`) follows the existing pattern.
