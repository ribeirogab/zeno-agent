# Multi-Profile CLI — Plan

**For this spec:** `[[spec]]`

## Approach

Bottom-up assembly so every phase produces working software. Discovery first (verify current versions and idioms of `drizzle-orm` / `drizzle-kit`, `dockerode`, the `gh` release JSON shape, and the GitHub REST releases endpoint). Then a new `@zeno/db` workspace with a single `./host` subpath: drizzle schema, generated migrations, typed queries, shared SQLite open-helper. After the storage primitive is in hand, scaffold `templates/profile/` (the read-only blueprint the CLI substitutes from on `profile create`) and rewrite `.gitignore` to belt-and-suspenders the entire `profiles/` path.

Phase 3 is the surgical kill of `config.yaml`: delete the static cron loader and its tests, prune the YAML branch from the profile watcher, simplify the worker entrypoint, simplify `git-identity.ts` to its `gh api` fallback only, and drop the YAML example from `agent/`. The worker still boots and resolves git identity through the existing `gh` path; nothing else moves. Verify with `pnpm run quality-gate`.

Phase 4 replaces `apps/cli`'s contents in-place. The brainstorm-time mock at `apps/cli-next/` is the UX target — its commands, output helpers, and spinner module move into `apps/cli/src/` while the mock orchestrator is replaced with a real `dockerode`-backed `DockerOrchestrator` and the JSON state file is replaced with calls to `@zeno/db/host`. Each command file is a thin handler that resolves arguments, talks to the orchestrator, queries the DB, and prints output. New commands (`profile create/edit/delete`, `upgrade`) live next to the refactored lifecycle commands. The legacy `compose.ts` lib, the `status`/`shell`/`build`/`docker`/`update` commands, and the JSON `state.ts` are deleted.

Phases 5 and 6 close the loop: rewrite `infra/install.sh` for the new path layout, drop `pnpm run docker:*` from the root `package.json`, refresh `README.md` and `CLAUDE.md`, delete the legacy compose files and the `apps/cli-next/` prototype, then manual end-to-end verification on a clean state followed by roadmap and PR housekeeping.

## Architecture

```
                       Operator (any cwd)
                              │
                              ▼
                  ~/.local/bin/zeno  (symlink)
                              │
                              ▼
       ~/.zeno/zeno-agent/apps/cli/dist/index.js  (citty CLI, ESM)
                              │
        ┌──────────────┬──────┴──────┬──────────────┐
        ▼              ▼             ▼              ▼
  lib/orchestrator  lib/templates  lib/upgrade   lib/output
  /docker.ts        .ts            .ts           lib/spinner
        │              │             │
        ▼              ▼             ▼
  /var/run/        templates/     gh release list
  docker.sock      profile/       (or REST fallback)
        │
        ▼                          @zeno/db/host
  Docker Engine API ◄── containers ──► state.db (drizzle, ~/.zeno/state.db)
  zeno-<profile>                       profiles, settings, audit_log,
  vol zeno-<profile>-workspace         schema_migrations
  vol zeno-<profile>-claude-home

  Profile container (zeno-agent:dev) — unchanged runtime, reads:
    /workspace               (named volume)
    /home/node/.claude       (named volume)
    /app/agent       (ro)    (bind: ~/.zeno/zeno-agent/agent)
    /app/profile     (ro)    (bind: ~/.zeno/profiles/<profile>)
```

## Phase Ordering

| Phase | Depends on | Goal |
|---|---|---|
| 0 — Discovery | — | Pin versions and idioms for drizzle-kit, drizzle-orm, dockerode, gh release JSON |
| 1 — `@zeno/db/host` package | 0 | drizzle schema + migrations + queries + tests; CLI not yet using it |
| 2 — Templates + .gitignore | — (independent) | `templates/profile/` exists; `profiles/` deleted; gitignore is belt-and-suspenders |
| 3 — Kill `config.yaml` | — (worker self-contained) | Worker boots without `config.yaml`; `gh api` fallback covers git identity |
| 4 — CLI rewrite | 1, 2 | `apps/cli` uses new orchestrator + DB + templates; surface matches spec ACs |
| 5 — install.sh + housekeeping | 4 | Repo is install-clean for the new path; legacy files deleted; docs updated |
| 6 — Manual verification + ship | 5 | End-to-end test on clean state; ROADMAP / PR / merge |

Phases 0 → 1 → 4 are the critical path. Phases 2 and 3 can run in parallel with 1 if needed; they have no dependencies on the new DB or CLI surface.
